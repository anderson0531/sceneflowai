# Multilanguage architecture

The platform ships 39 languages. Text falls into three kinds that need three
different mechanisms, and the most common way app localization fails is treating
them as one.

| Kind | Examples | Mechanism |
| --- | --- | --- |
| **Chrome** | buttons, labels, dialog titles, toasts | `next-intl` catalogs under `messages/app/{locale}/{surface}.json` |
| **Creative content** | loglines, synopses, beats, dialogue | authored natively via `localeDirective()`; cached MT as fallback |
| **Machine-facing** | `videoPrompt`, `startFramePrompt`, wardrobe text | never translated |

## Three language settings

They are deliberately separate. A creator may read the studio in Spanish, write
for an English-language market, and deliver dubs in eight more.

| Setting | Stored | Controls |
| --- | --- | --- |
| Interface | `users.preferred_locale`, mirrored to the `sf-locale` cookie | app chrome |
| Story | `users.story_locale`, overridable at `metadata.i18n.sourceLocale` | language new AI content is authored in |
| Delivery | `productionTarget.language` per scene | narration, dubs, rendered video |

## Layer 1 — chrome catalogs

Six surfaces: `common`, `dashboard`, `settings`, `series`, `blueprint`,
`production`. `common` loads everywhere, so keep it small; each route group loads
only its own surface on top. The split exists because the landing catalog is
already 141 KB in English and 342 KB in Thai — folding app chrome into one blob
would ship the whole product's UI text to someone reading the Dashboard.

Providers sit at the route-group layouts (`AppMessagesProvider`, a server
component). The root layout uses `ClientAppMessagesProvider` for the header
instead, because reading cookies in the root layout would opt every static
marketing and legal page into dynamic rendering.

### Commands

```bash
npm run i18n:app:build-en        # lint English catalogs, refresh fingerprints
npm run i18n:app:check           # CI: fail if fingerprints are stale
npm run i18n:app:generate        # translate only keys whose English changed
npm run i18n:app:generate:full   # re-translate everything
npm run lint:i18n                # forbid new hardcoded JSX text in converted files
```

Scoped runs:

```bash
npx tsx scripts/generate-app-locale-messages.ts --locales=es,ja --surfaces=blueprint
```

`messages/app/_fingerprints.json` maps each key to a hash of its English value.
Only changed keys are re-sent, and the file only advances after a run completes,
so an aborted run does not mark changed keys as done.

### Extraction

```bash
npx tsx scripts/i18n-extract.ts --surface=blueprint            # dry run
npx tsx scripts/i18n-extract.ts --surface=blueprint --write    # merge into en catalog
```

The codemod finds JSX text nodes, display-only string props, and `toast.*` calls,
and skips anything inside `translate="no"`, anything matching the machine-field
rules, and anything that does not look like prose. Keys are
`surface.component.slugifiedText`, so re-running is idempotent.

**Rewriting call sites is a separate, reviewed step.** The codemod reports
candidates; a human decides which are real. Roughly 15% of candidates on a large
surface are sentence fragments split across JSX elements (`"Improve ("`,
`"applied — re-analyze to update your official score."`) that must be recomposed
into one ICU message rather than translated piecemeal.

Rollout state:

| Surface | Candidates | Converted |
| --- | --- | --- |
| `common` (shell) | ~85 | `GlobalHeader`, all of `components/i18n` |
| `settings` | ~120 | layout nav, profile page, Languages card |
| `dashboard` | ~310 | not yet |
| `series` | — | not yet |
| `blueprint` | ~910 | not yet |
| `production` | — | not yet |

As each file is converted, add it to `eslint.i18n.config.mjs` so the guard keeps
it converted. Un-extracted surfaces are covered by the Google Translate fallback
(see below), so there is no coverage gap during migration.

In development, the `i18n` button in the bottom corner of the Dashboard
highlights text that reached the screen in English while the interface locale is
something else.

## Layer 2 — creative content

### Entry: two seams, no client changes

A creator types in their own language from any of ~55 dialogs, and there is no
shared client HTTP layer — ~116 files call `fetch` directly. Asking each of them
to attach a locale would regress the moment someone adds a dialog, so both rules
live on the server in `src/i18n/server/requestLocale.ts`:

| Seam | Applies to | Rule |
| --- | --- | --- |
| `resolveRequestStoryLocale(request, options)` | every route that reads typed text | recovers the language from the `sf-locale` cookie, but only after `resolveStoryLocale` has exhausted explicit → project → series → account |
| `englishForModel(text, storyLocale, glossary)` | anything that becomes a generation prompt | translates to English, cache-first and glossary-protected; a no-op for English |

The asymmetry is deliberate. Creative *direction* stays in the creator's
language — the text models read it natively and `localeDirective` makes them
answer in it. Anything fed to Imagen, Veo or Kling is normalized to English,
because those models degrade on non-English prompts and the damage is invisible:
the render just gets worse, with nothing pointing back at a language setting.

The cookie is consulted last so a blueprint written in Japanese keeps authoring
in Japanese even while its creator reads the studio in Spanish. Workers have no
request, so they call `resolveStoryLocale` directly and capture the locale at
enqueue time.

`src/__tests__/userInputLocale.test.ts` scans every route for the body fields
that carry typed text and fails when one skips a seam, because neither failure
mode raises an error at runtime. Routes that legitimately need neither — TTS
synthesis, speech-model briefs, prompt classifiers — are allowlisted there with
a reason.

One consequence worth knowing: deterministic English keyword matching cannot
read native direction. `inferTargetedSections` decides which blueprint sections
a revision touches from words like "beats" and "pacing", so guided revise sends
an English copy of the direction (`intentTextForRouting`) for routing and
validation while every prompt keeps the creator's own words.

### Generate natively (primary)

`localeDirective(storyLocale, { properNouns, keepEnglishFields })` in
`src/lib/prompts/localeDirective.ts` is injected into the treatment, series,
script, beat and refine prompt builders. Asking the model to write in the target
language beats translating its English output on idiom, register, names and
performability, and costs nothing extra.

It returns an empty string for English, so English prompts are byte-identical to
before.

Resolution is server-authoritative — `resolveStoryLocale()` walks explicit →
project → series → account → English — so a route whose caller forgets to pass a
locale does not silently fall back to English.

### Translate (fallback)

`POST /api/i18n/content` translates already-authored content. It is
authenticated, batched, deduplicates by text, and runs every item through the
field registry. Results are cached in `content_translations`, keyed on a hash of
the normalized source text — so an identical string is paid for once
platform-wide, an edit produces a new key rather than a stale hit, and orphans
are LRU-evictable.

The older `/api/translate/*` endpoints remain for delivery-language work reached
from public share and embed surfaces. They now read through the same cache.

### The field registry

`src/i18n/content/fieldRegistry.ts` classifies every stored field path:

- `display` — localize it
- `spoken` — follows the delivery language, not the interface language
- `machine` — never translate; fed to Imagen/Veo/Kling
- `opaque` — ids, urls, enums, proper nouns

**Unclassified paths resolve to `opaque`.** The asymmetry is the point: failing
to translate a label is a small UX wart, while translating a `videoPrompt`
degrades render quality in a way nobody would trace back to a language setting.
An unenumerated `*Prompt` field is caught by rule rather than needing to be
listed.

Adding a prose field to a content type without classifying it will fail
`src/__tests__/contentFieldRegistry.test.ts`.

### Editing translated content

`LocalizedField` is the primitive. Entity localization is single-master: one
language is the source of record, everything else is derived.

- Editing a translated value writes an **override** at
  `metadata.i18n.overrides[locale][path]`, which MT never overwrites. Same
  relationship `messages/tier-a/` has with the landing catalogs.
- **Rewrite in {language}** promotes the reader's language to source of record
  and drops the now-stale derived translations.
- `machine` fields render locked, with the reason stated.

## Layer 3 — Google Translate fallback

Scoped by `src/config/i18n/gtSurfaces.ts`. **Not enabled inside the studios**:
Google Translate rewrites DOM text nodes underneath React, which in
`vision/[projectId]/page.tsx` causes reconciliation crashes and mangles input
values. It covers read-mostly surfaces — help, legal, share, embed, review — and
is always opt-in.

Mark anything that must survive it with `translate="no"`: brand marks, prompt
textareas, code and JSON views, credit amounts, timecodes, ids.

## Adding a language

1. Add it to `PLATFORM_LANGUAGES` in `src/config/landingTranslateLanguages.ts`
   with its endonym and English exonym.
2. Add a flag to `LOCALE_FLAGS` in `src/components/i18n/LocalePicker.tsx`.
3. If it is right-to-left, add it to `RTL_LOCALES` in `src/i18n/locale.ts`.
4. If it needs a non-Latin font, add a `html:lang(xx)` rule in `globals.css`.
5. Run `npm run i18n:app:generate -- --locales=xx`.
